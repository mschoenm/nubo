# CI and nightly runs

What runs where, and why. The checks to run yourself before pushing are listed in the root `AGENTS.md`.

## Pull requests and main

- CI (`.github/workflows/ci.yml`) runs `cargo test-roms`, together with `cargo cpu-tests` and `cargo save-states` (with the games cached), on every pull request and push to main, next to `cargo fmt --check`, both clippy runs (`--workspace --all-targets` and `-p nubo --target wasm32-unknown-unknown`) and `cargo doc` with warnings as errors, `cargo deny check licenses bans sources` (`deny.toml` allows only GPLv3-compatible licenses), `cargo test --workspace` on Linux, `cargo xtask build-web --quick`, `cargo xtask release-notes` (the newest release in the AppStream file must be the version in `Cargo.toml`) and `cargo xtask rust-version` (no crate the app or the RetroArch core is built from needs a newer Rust than `rust-version`).
- Pull requests should get their answer in a minute or two, so every CI job is meant to take about a minute, and anything slower goes in the nightly workflow, which every release runs too: a problem may reach main, but never a release.
- `.github/workflows/platforms.yml`, `cargo test --workspace` on macOS and Windows, doesn't run on pull requests: the same tests on Linux catch nearly everything, so it runs nightly (below), and by hand (`workflow_dispatch`) when a change needs it sooner, such as one to file paths, line endings or the build.
- A push to main that passes CI is built with the optimized `wasm-release` profile and published to GitHub Pages, with the download page at `download/` (`.github/workflows/deploy.yml`, a workflow of its own so pull requests don't list a deploy job that is always skipped for them).
- Branch protection only requires the "CI passed" job, which needs all the others.

## Nightly

- The slow checks run nightly (`.github/workflows/nightly.yml`, at 23:17 UTC, which is 01:17 Amsterdam time in summer and 00:17 in winter; GitHub can start scheduled runs late when it is busy), together with CI itself, so whatever a new release of Rust or another dependency breaks shows up that night: `cargo test --workspace` on macOS and Windows (`platforms.yml`), `cargo test-roms --verify-boot`, `cargo benchmark --check-save-states` and the lazy-against-`eager` fingerprint comparison on all test ROMs (both split over several machines with `--shard`, from one build of the benchmark), 10,000 random PPU scenes compared with running dot by dot (`gpu/tests/random_scenes.rs`, with a new seed each night, which a failure reports; CI tries 18), `cargo deny check advisories`, the Flatpak build for x86_64 and ARM (`.github/workflows/flatpak.yml`, which plays a game in the installed Flatpak with `measure-efficiency`, since the Flatpak is what Linux users get and nothing else runs it, and runs Flathub's linter on the AppStream file and the build, pinned by digest, warning when Flathub publishes a newer one), the Windows installer and zip (`.github/workflows/windows.yml`, which validates the MSI, plays a game from the unpacked zip and from an installed Nubo, and installs, updates, downgrades and uninstalls quietly with choices given on the command line) and the RetroArch core's zips for Linux x86_64 and ARM, Windows and macOS (`.github/workflows/libretro.yml`, which plays a game in the RetroArch Ubuntu packages with run-ahead, rewind and an auto-saved state). Pull requests don't run these packaging workflows: they rarely fail, and a failure shows up that night, before a release can ship it. Start one by hand (`workflow_dispatch`) when a change needs it sooner, such as one to how a package is built.
- After the Windows job, `.github/workflows/shootout.yml` runs the GB Emulator Shootout's own harness on the zip that job built, the file a release publishes and the Shootout downloads: in a checkout of the Shootout at the commit the test ROM runner pins, with Nubo's harness class `.github/shootout/nubo.py`, it starts the real `nubo.exe` on a GitHub Windows machine for every test and compares screenshots of its window with the references. It fails unless every Shootout test in `passing.txt` passes there too, so it catches what the headless run can't see (the window's title and size, settings or saves kept between tests, the startup time), and keeps `nubo.json` with each test's screenshot as its artifact. It takes about 5 minutes after the Windows job. Pull requests don't run it; runs started by hand build their own zip with `windows.yml` first. See `docs/SHOOTOUT_PLAN.md`, "Part 3 in CI".
- Its `metrics` job starts once every other job has finished, so nothing else of the run is busy while it measures and every night is measured alike (only the checks are split over machines). It measures speed on the homebrew games of `cargo xtask benchmark-roms`, instructions per emulated second under cachegrind (steadier than time on shared machines), the efficiency harness and the build sizes, and writes them with every job's result (`tests` in `night.json`, keyed by job; the Shootout harness job's key is `shootout_harness`, since `shootout` holds the published score, and a job skipped because the one it needs failed counts as a regression too) to the repository's wiki (`metrics.jsonl` and the "Nightly metrics" page) together with the part the nightly review reads tonight. `cargo xtask metrics` flags a value that moved too far from its 14-night median (speed more than 10% lower, instructions 2% higher, the build sizes 5% and battery use 10%). A night also keeps the processor model of its machine (`cpu`, from `/proc/cpuinfo`), and speed is compared only with nights on the same model: GitHub gives the job machines up to twice as fast now and then, and nights on them made normal nights look 10% slow (issue #314). Until 5 earlier nights ran on tonight's model, speed isn't judged, and the page says so; the other values are compared with every night.
- The metrics also keep the test ROM counts of the `verify-boot` job's `cargo test-roms --verify-boot`: its `total` line, and its `shootout` line, Nubo's score on the GB Emulator Shootout's published tests and the rank it would have in that table (`shootout` in `night.json`, with the publication it was counted against, and the first line of the "Nightly metrics" page, until Nubo is in the published table itself; see `docs/SHOOTOUT_PLAN.md`). Neither has a regression threshold: a test that stops passing already fails CI, and the page's history shows the trend. `tools/nubo-test-rom-runner/shootout_published.txt` holds the published table, read once with `cargo xtask shootout-scoreboard <commit>`, so no run downloads it.
- Only scheduled runs write to the wiki, since the rotation counts the changes since the last run that did: a run started by hand would hide the day's changes from the review. Pushing to the wiki needs the `WIKI_TOKEN` secret, which only the `wiki` job gets: it runs on a machine of its own after `metrics`, also on a night where another job failed (the night most worth recording), takes just the four files from its artifact and pushes them, so no code that cargo builds ever runs where the token is; runs that don't push keep the files as their artifact.
- At 04:07 Amsterdam time a Claude cloud routine follows `docs/NIGHTLY_REVIEW.md`: it reviews the day's changes and that part, fixes what is clearly better as long as every fingerprint stays the same, and opens a `claude/nightly-<date>` pull request. Anything that regressed or failed, and any bug it finds but doesn't fix, becomes an issue labeled `nightly`, which it closes again once a later change fixes it.
- Every hour another routine follows `docs/ISSUE_TRIAGE.md`: it brings the maintainer's issue-triage page up to date with every open issue and an assessment of it, and starts a session for each issue the maintainer starts there; most hours it finds nothing to do and stops after a quick check.
- Releases run the nightly workflow, CI included (see the `release` skill, `.claude/skills/release/SKILL.md`).

## Nightly builds

When every check of a scheduled or hand-started nightly run passes (the Metrics job and the wiki push, which measure and record rather than check, may fail) and `main` has changed since the last one, `.github/workflows/nightly-build.yml` publishes its Flatpaks, Windows installer and zip and RetroArch cores as the `nightly` pre-release (named like `Nubo-nightly-<date>-linux-x86_64.flatpak`, `Nubo-nightly-<date>-windows-x64.msi` and `Nubo-nightly-<date>-libretro-linux-x86_64.zip`), replacing the one before; it is the same app as the releases, so installing it with `--reinstall` replaces the installed version. The Windows build of a nightly run knows it is one (`windows.yml`'s `nightly` input, which `nightly.yml` sets unless a release runs it) and carries the night's date in its file names and in the name Windows shows for the installed app ("Nubo (nightly <date>)"); `nightly-build.yml` reads the date from the MSI's name, so every file of the night gets the same one.

## Caches

GitHub keeps up to 10 GB of caches for the repository and evicts the least recently used ones beyond that, and any cache not used for 7 days.

- The Rust jobs cache their compiled dependencies with `Swatinem/rust-cache`, saved only on main, so pull requests restore main's caches but never add their own. Jobs that build the same thing share a cache through `shared-key` (`tests`, `release`, `web-quick`, `web-release`). The others get one per job id, but a job id is unique only within its workflow, so jobs with the same id on the same system get a key of their own too (`windows-app` and `libretro`, both `build` on Windows). A key is the name, the operating system and processor, a hash of Rust's version and the `CARGO_*` and `RUST*` variables, and a hash of `Cargo.lock`, so a new Rust or `Cargo.lock` saves a new cache.
- Every workflow that uses rust-cache sets `CARGO_PROFILE_DEV_DEBUG` and `CARGO_PROFILE_TEST_DEBUG` to `0`: nobody runs a debugger in CI, a panic's message still gives its file and line, and debug info was most of the size of the dev builds' caches. It makes the tests' dependencies about 40% smaller, compressed, and builds them faster; `line-tables-only` saved half as much. The variables are in the keys, so they must be the same in every workflow, or the nightly jobs that share CI's `release` cache would miss it. The release profile, which the test ROMs, the benchmarks and the Metrics job's Valgrind run use, has no debug info anyway; cachegrind counts instructions without it.
- The test ROMs, the JSON CPU tests and the benchmark games are cached under a hash of their pins (`.github/actions/test-roms`, and `benchmark-roms` in `ci.yml`).
- The RetroArch play test in `libretro.yml` caches the Ubuntu packages it installs, under a hash of the version of `retroarch` Ubuntu offers after `apt-get update`, so the nightly needs Ubuntu's mirror only after a new RetroArch version, and still tests what Ubuntu ships. apt checks each cached file against the package lists, and downloads what is missing or doesn't match.
- `.github/workflows/caches.yml` runs after every CI, Nightly and Deploy run on main. Caches on main whose keys are the same but for their trailing hashes form a group, and it deletes all but the newest of each, so the old caches of a previous `Cargo.lock` or Rust don't wait 7 days for GitHub to evict them. Its step summary lists the caches that stay, with their sizes; start it by hand to see the list.

## Toolchain and dependency updates

Rust (the `stable` channel), crates, GitHub Actions (pinned to commits, which Dependabot moves to each release), and tools such as cargo-deny, Flathub's linter and the WiX Toolset all follow their newest stable release, and never a pre-release unless nothing else works. When an update breaks something, the nightly run fails, and that is where it gets fixed. The fuzz targets in `fuzz/` use the nightly toolchain, which `cargo-fuzz` needs; they are outside the Cargo workspace, no job here builds them, and only a full review runs them (`fuzz/AGENTS.md`). The other exception is what others build from Nubo's source: the Flatpak is built with exactly what Flathub would build it with (Flathub's newest freedesktop runtime, its SDK's Rust and `Cargo.lock`), and its build fails when either moves on. Test data (the test ROMs, the benchmark games and the emulators compared against) stays pinned, since results and kept save states depend on its exact content. The RetroArch core's Linux zips are built on Ubuntu 24.04 rather than the newest Ubuntu, since a core runs with the C library of the RetroArch it is loaded into, and one built on a newer Ubuntu could need a newer glibc than players have (`.github/workflows/libretro.yml`).

Flathub's linter, which `flatpak.yml` runs on the AppStream file and the build, is pinned by digest (`LINTER` there), so an image pushed under its tag can't run there. The job uploads the Flatpak before the linter runs and gives it only what it reads: the AppStream file's folder and the list of exceptions, read-only, and a copy of the build's repository. Both must pass, apart from the two screenshot checks listed in `.github/flatpak-lint-exceptions.json`: only Flathub's own build copies the screenshots to its server and points the AppStream data there, and doing that here would leave the published Flatpaks without screenshots in software centers. The controller permission (`--device=input`) comes with `--device-if=all:!has-input-device`, so Flatpak before 1.15.6, which has no `input` device, gives the app every device instead, as Flathub asks. The job warns when Flathub has published a newer image, and the nightly review reports that warning (`docs/NIGHTLY_REVIEW.md`); the digest is then raised by hand, and a check Flathub added fails the nightly run from then on.

The WiX Toolset, which builds the Windows MSI, is installed unpinned with `dotnet tool install --global wix`. From version 7 it refuses to run until its Open Source Maintenance Fee agreement is accepted, which `windows.yml` does with `wix eula accept wix7`: the maintainer read and accepted it on 2026-10-14. The fee is only owed by those making US$10,000 or more a year from work that uses WiX, so Nubo owes nothing. A new major version asks for a new agreement under a new name, so the nightly run fails at that step until the maintainer has read it and the name in `windows.yml` is raised.

Rust follows the stable channel (`rust-toolchain.toml`), and Dependabot proposes new crates and actions (pinned to commits) every day. The Flatpak is built with the freedesktop SDK's Rust instead, as Flathub builds it, which can lag behind, so `rust-version` in the root `Cargo.toml` is that version for the crates the app is built from: clippy then rejects newer standard library items in pull requests. The workspace uses Cargo's resolver 3, so `cargo update` picks the newest version of each crate that still builds with that Rust, where one exists. A pull request that raises a dependency to a version needing a newer Rust (by hand, or Dependabot's) fails CI's `cargo xtask rust-version` instead, which checks every crate the app (which the Flatpak builds) and the RetroArch core (which declares the same `rust-version`) are built from, on the Flatpak's two systems, against `rust-version`. The Flatpak build prints the SDK's Rust and fails when it isn't `rust-version`, and fails when Flathub has a newer freedesktop runtime than `RUNTIME_VERSION` in `xtask/src/flatpak.rs`; both are then raised by hand.
