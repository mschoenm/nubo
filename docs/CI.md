# CI and nightly runs

What runs where, and why. The checks to run yourself before pushing are listed in the root `AGENTS.md`.

## Pull requests and main

- CI (`.github/workflows/ci.yml`) runs `cargo test-roms`, together with `cargo cpu-tests` and `cargo save-states` (with the games cached), on every pull request and push to main, next to `cargo fmt --check`, both clippy runs (`--workspace --all-targets` and `-p nubo --target wasm32-unknown-unknown`) and `cargo doc` with warnings as errors, `cargo deny check licenses bans sources` (`deny.toml` allows only GPLv3-compatible licenses), `cargo test --workspace` on Linux, `cargo xtask build-web --quick` and `cargo xtask release-notes` (the newest release in the AppStream file must be the version in `Cargo.toml`).
- Pull requests should get their answer in a minute or two, so every CI job is meant to take about a minute, and anything slower goes in the nightly workflow, which every release runs too: a problem may reach main, but never a release.
- `.github/workflows/platforms.yml`, `cargo test --workspace` on macOS and Windows, doesn't run on pull requests: the same tests on Linux catch nearly everything, so it runs nightly (below), and by hand (`workflow_dispatch`) when a change needs it sooner, such as one to file paths, line endings or the build.
- A push to main that passes CI is built with the optimized `wasm-release` profile and published to GitHub Pages (`.github/workflows/deploy.yml`, a workflow of its own so pull requests don't list a deploy job that is always skipped for them).
- Branch protection only requires the "CI passed" job, which needs all the others.

## Nightly

- The slow checks run nightly (`.github/workflows/nightly.yml`, at 01:17 Amsterdam time; GitHub can start scheduled runs late when it is busy), together with CI itself, so whatever a new release of Rust or another dependency breaks shows up that night: `cargo test --workspace` on macOS and Windows (`platforms.yml`), `cargo test-roms --verify-boot`, `cargo benchmark --check-save-states` and the lazy-against-`eager` fingerprint comparison on all test ROMs (both split over several machines with `--shard`, from one build of the benchmark), 10,000 random PPU scenes compared with running dot by dot (`gpu/tests/random_scenes.rs`, with a new seed each night, which a failure reports; CI tries 18), `cargo deny check advisories`, the Flatpak build for x86_64 and ARM (`.github/workflows/flatpak.yml`, which plays a game in the installed Flatpak with `measure-efficiency`, since the Flatpak is what Linux users get and nothing else runs it, and runs the newest Flathub linter on the AppStream file, unpinned so a nightly run fails as soon as Nubo couldn't be published on Flathub), the Windows installer and zip (`.github/workflows/windows.yml`, which validates the MSI, plays a game from the unpacked zip and from an installed Nubo, and installs, updates, downgrades and uninstalls quietly with choices given on the command line) and the RetroArch core's zips for Linux x86_64 and ARM, Windows and macOS (`.github/workflows/libretro.yml`, which plays a game in the RetroArch Ubuntu packages with run-ahead, rewind and an auto-saved state), all of which also run on pull requests that change how they are built or `Cargo.lock`, without holding them up.
- After the Windows job, `.github/workflows/shootout.yml` runs the GB Emulator Shootout's own harness on the zip that job built, the file a release publishes and the Shootout downloads: in a checkout of the Shootout at the commit the test ROM runner pins, with Nubo's harness class `.github/shootout/nubo.py`, it starts the real `nubo.exe` on a GitHub Windows machine for every test and compares screenshots of its window with the references. It fails unless every Shootout test in `passing.txt` passes there too, so it catches what the headless run can't see (the window's title and size, settings or saves kept between tests, the startup time), and keeps `nubo.json` with each test's screenshot as its artifact. It takes about 5 minutes after the Windows job. Pull requests that change the workflow or the class, and runs started by hand, build their own zip with `windows.yml` first, without holding pull requests up. See `docs/SHOOTOUT_PLAN.md`, "Part 3 in CI".
- Its `metrics` job starts once every other job has finished, so nothing else of the run is busy while it measures and every night is measured alike (only the checks are split over machines). It measures speed on the homebrew games of `cargo xtask benchmark-roms`, instructions per emulated second under cachegrind (steadier than time on shared machines), the efficiency harness and the build sizes, and writes them with every job's result to the repository's wiki (`metrics.jsonl` and the "Nightly metrics" page) together with the part the nightly review reads tonight.
- The metrics also keep the test ROM counts of the `verify-boot` job's `cargo test-roms --verify-boot`: its `total` line, and its `shootout` line, Nubo's score on the GB Emulator Shootout's published tests and the rank it would have in that table (`shootout` in `night.json`, with the publication it was counted against, and the first line of the "Nightly metrics" page, until Nubo is in the published table itself; see `docs/SHOOTOUT_PLAN.md`). Neither has a regression threshold: a test that stops passing already fails CI, and the page's history shows the trend. `tools/nubo-test-rom-runner/shootout_published.txt` holds the published table, read once with `cargo xtask shootout-scoreboard <commit>`, so no run downloads it.
- Only scheduled runs write to the wiki, since the rotation counts the changes since the last run that did: a run started by hand would hide the day's changes from the review. Pushing to the wiki needs the `WIKI_TOKEN` secret, which only the `wiki` job gets: it runs on a machine of its own after `metrics`, takes just the four files from its artifact and pushes them, so no code that cargo builds ever runs where the token is; runs that don't push keep the files as their artifact.
- At 04:07 Amsterdam time a Claude cloud routine follows `docs/NIGHTLY_REVIEW.md`: it reviews the day's changes and that part, fixes what is clearly better as long as every fingerprint stays the same, and opens a `claude/nightly-<date>` pull request. Anything that regressed or failed, and any bug it finds but doesn't fix, becomes an issue labelled `nightly`, which it closes again once a later change fixes it.
- Every hour another routine follows `docs/ISSUE_TRIAGE.md`: it brings the maintainer's issue-triage page up to date with every open issue and an assessment of it, and starts a session for each issue the maintainer ticks there; most hours it finds nothing to do and stops after a quick check.
- Releases run the nightly workflow, CI included (see the `release` skill, `.claude/skills/release/SKILL.md`).

## Nightly builds

When a scheduled or hand-started nightly run passes and `main` has changed since the last one, `.github/workflows/nightly-build.yml` publishes its Flatpaks, Windows installer and zip and RetroArch cores as the `nightly` pre-release (named like `Nubo-nightly-<date>-linux-x86_64.flatpak`, `Nubo-nightly-<date>-windows-x64.msi` and `Nubo-nightly-<date>-libretro-linux-x86_64.zip`), replacing the one before; it is the same app as the releases, so installing it with `--reinstall` replaces the installed version. The Windows build of a nightly run knows it is one (`windows.yml`'s `nightly` input, which `nightly.yml` sets unless a release runs it) and carries the night's date in its file names and in the name Windows shows for the installed app ("Nubo (nightly <date>)"); `nightly-build.yml` reads the date from the MSI's name, so every file of the night gets the same one.

## Toolchain and dependency updates

Rust (the `stable` channel), crates, GitHub Actions (pinned to commits, which Dependabot moves to each release), and tools such as cargo-deny, Flathub's linter and the WiX Toolset all follow their newest stable release, and never a pre-release unless nothing else works. When an update breaks something, the nightly run fails, and that is where it gets fixed. The fuzz targets in `fuzz/` use the nightly toolchain, which `cargo-fuzz` needs; they are outside the Cargo workspace, no job here builds them, and only a full review runs them (`fuzz/AGENTS.md`). The other exception is what others build from Nubo's source: the Flatpak is built with exactly what Flathub would build it with (Flathub's newest freedesktop runtime, its SDK's Rust and `Cargo.lock`), and its build fails when either moves on. Test data (the test ROMs, the benchmark games and the emulators compared against) stays pinned, since results and kept save states depend on its exact content. The RetroArch core's Linux zips are built on Ubuntu 24.04 rather than the newest Ubuntu, since a core runs with the C library of the RetroArch it is loaded into, and one built on a newer Ubuntu could need a newer glibc than players have (`.github/workflows/libretro.yml`).

The WiX Toolset, which builds the Windows MSI, is installed unpinned with `dotnet tool install --global wix`. From version 7 it refuses to run until its Open Source Maintenance Fee agreement is accepted, which `windows.yml` does with `wix eula accept wix7`: the maintainer read and accepted it on 2026-10-14. The fee is only owed by those making US$10,000 or more a year from work that uses WiX, so Nubo owes nothing. A new major version asks for a new agreement under a new name, so the nightly run fails at that step until the maintainer has read it and the name in `windows.yml` is raised.

Rust follows the stable channel (`rust-toolchain.toml`), and Dependabot proposes new crates and actions (pinned to commits) every day. The Flatpak is built with the freedesktop SDK's Rust instead, as Flathub builds it, which can lag behind, so `rust-version` in the root `Cargo.toml` is that version for the crates the app is built from: clippy then rejects newer standard library items in pull requests. The Flatpak build prints the SDK's Rust and fails when it isn't `rust-version`, and fails when Flathub has a newer freedesktop runtime than `RUNTIME_VERSION` in `xtask/src/flatpak.rs`; both are then raised by hand.
