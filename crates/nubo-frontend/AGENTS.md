# nubo-frontend

Everything a Nubo app needs that isn't drawing, so each app (the Iced app in `frontends/nubo` today; the RetroArch core, and maybe an iOS, GTK or web UI later, see `docs/RESTRUCTURE_PLAN.md`) only has to draw and handle input. `src/lib.rs` lists the modules and features; each module's docs explain it. This guide explains how they fit together.

```bash
cargo test -p nubo-frontend --all-features            # Every test, files and localStorage keys included
cargo test -p nubo-frontend --no-default-features      # What the RetroArch core builds: no storage, no session
cargo clippy -p nubo-frontend --all-features --all-targets -- -D warnings
cargo clippy -p nubo-frontend --no-default-features --features web,gamepads --target wasm32-unknown-unknown -- -D warnings
```

`cargo test --workspace` builds it with the features the Iced app turns on for the host (`desktop` and `gamepads`); check the other combinations above when a change touches a feature's code.

## How It Fits Together

- **No UI toolkit.** It never names Iced, so nothing an app shows depends on one. It reports to the app through `futures` channels (controllers) and callbacks (new frames, the library's folder watcher), which the app turns into its own events; the Iced app does that in `frontends/nubo/src/subscriptions.rs`. A callback may run on a thread of this crate's (the emulator thread, the watcher's thread) and must never block a thread the app's executor polls.
- **Features per platform.** `desktop` keeps the data in files and plays the sound through cpal, `web` keeps settings, battery saves and cheats in localStorage and save states, the library and the games' files in IndexedDB (`storage/indexed_db.rs`, read into memory once when the app starts, so reading stays synchronous, and written in the background) and plays through WebAudio, and `gamepads` reads controllers with gilrs. The browser has no folders, so its library keeps the games' files itself (`library::KEEPS_GAMES`). Without `desktop` or `web` it keeps nothing (`storage::NoStorage`) and has no `session`, which is how the RetroArch core builds it. Which way a game is paced follows the target: by the sound card on every target with threads (`session/sound_card.rs`), by the screen's refreshes in the browser (`session/screen_refresh.rs`, with `pacing.rs`). A host like RetroArch that calls once per frame needs no session and calls `Emulator::run_frame` itself.
- **Slow work** (scans, title screen captures, box art downloads, picture decoding) goes through `background::run`. On the desktop it runs the work on a thread of its own, so apps keep it off their UI thread; in the browser, which has a single thread, it runs the work in place when the future is first polled, so the work still holds up the page while it runs. Work that would hold it up long runs in pieces there instead, with `background::pause` in between (title screens, `Cache::title_screen`), and downloads use the browser's `fetch` (`library/box_art/fetch.rs`).
- **Rewind and screen effects stay out of the emulation.** The session keeps a save state every few frames while a game runs (`session/history.rs`, the newest whole and the older ones as differences) and steps back through them while rewinding, silently. Color correction and frame blending (`lcd.rs`) change the picture after the emulator made it. None of it changes what the emulator does, so they need no test ROM or fingerprint runs. The Shootout's harness does take screenshots of the app, so every choice that changes the picture is a field of `settings::ScreenLook`, which `ScreenLook::RAW` (the app's `--raw-screen`) must turn off.
- **Scenes** (`scenes.rs`) are recorded moments of a game that the documentation's screenshots are made from again: the format of their folders, read by the app and by `cargo xtask`. A run that shows one keeps its data in a folder of its own (`storage::files::use_folder`, which every lookup of the player's folders goes through), and the session runs its frames exactly (`Command::RunFrames`, with `Emulator::run_frame`), so a scene always gives the same picture.
- **Pictures are `picture::Picture`**: plain RGBA pixels that an app turns into its own kind of image once, keeping it with the picture (`Picture::drawn`).

## Players' Data Is Permanent

What this crate stores must read back the same in every later version, as `docs/RESTRUCTURE_PLAN.md`'s goals ask: the same files in the same folders (`ProjectDirs::from("", "", "Nubo")`, `storage/files.rs`), the same `settings.toml`, `library.toml`, `cheats/*.toml`, `.sav`, `.rtc` and `.state` formats, the same localStorage keys (`storage/local_storage.rs`), and the same IndexedDB database, object stores and entry names (`storage/indexed_db.rs`, `save_states/browser_store.rs`, `library/browser_store.rs`). What can't be read is never written over: an unreadable settings, cheats or library file (or browser entry) is kept aside under the first free `<name>.kept-<number>.<extension>` (`storage::kept_name`, `Storage::keep_aside`), as an unloadable save state is (`<slot>.kept-<number>.state`), and those names are permanent too. One that can't be read at all, or can't be kept aside (a file another program holds open), stays where it is. The library and cheats report it with `storage::Unreadable::saving_is_safe`, and then nothing is saved over it that run: the library doesn't save its list of games and a game doesn't save its cheats. Settings report it with `Loaded::saving_is_safe`, and then an app saves nothing on its own (such as the window's size), only what the player changes, which writes the defaults and that change over the file. A battery save (`.sav`, `.rtc`) that can't be read is reported, and the game saves nothing to it that run (`battery.rs`). The tests guard it:

- `src/settings/tests/settings.toml` is a settings file written by an earlier version; it must read back equal and write back byte for byte.
- `tests/existing_data_folder/` is a whole data folder written by an earlier version (settings, battery saves with a clock, save states with pictures, cheats, the library cache with its pictures); `tests/existing_data_folder.rs` reads it back through the public API and writes it again byte for byte.
- The browser's localStorage keys, IndexedDB names and entry names are checked by name in `storage/local_storage/tests.rs`, `storage/indexed_db/tests.rs` and the browser stores' tests (`save_states/browser_store/tests.rs`, `library/browser_store/tests.rs`).
- Both are compared byte for byte, so `.gitattributes` keeps Git from changing their line endings on Windows. Never regenerate them with newer code to make a test pass: a failing test there means players would lose data.
