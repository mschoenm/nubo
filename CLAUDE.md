# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Nubo (formerly RetroBoy, a fork of smparsons/retroboy) is a cycle-accurate Game Boy (DMG) and Game Boy Color (CGB) emulator written in Rust. The core emulator runs through an Iced frontend, natively on the desktop and compiled to WebAssembly in the browser. Nubo is licensed under GPL-3.0-or-later (`LICENSE`); the code that came from RetroBoy remains Apache-2.0 (`LICENSE-APACHE`), and `NOTICE` keeps its attribution.

## Build Commands

Everything is driven by cargo and works on Windows, macOS, and Linux with only a Rust toolchain installed (the newest stable, which `rust-toolchain.toml` asks for; `rustup update` gets it; Linux additionally needs `libasound2-dev`, `libudev-dev` and `pkg-config` for audio and controllers). The packaging tasks need their platform's tools, and `cargo xtask compare-emulators` builds other emulators from their C and C++ sources; nothing else needs them. The commands below are aliases defined in `.cargo/config.toml`.

```bash
# Core library
cargo build                   # Build the core crates (default workspace members)
cargo test                    # Run core emulator tests
cargo check --workspace       # Check every crate, including frontends and xtask
cargo clippy --workspace --all-targets   # Lint every crate; must stay free of warnings
cargo clippy -p nubo --target wasm32-unknown-unknown   # Also lint the browser-only files of the Iced frontend
cargo test -p nubo            # Run the Iced frontend's tests (it isn't a default member)
cargo fmt --all               # Format with rustfmt
cargo test-roms               # Run the test ROM suites and compare with the list of passing tests
cargo test-roms mooneye       # Only run tests whose name contains "mooneye" (e.g. "cgb blargg", "dmg mealybug")
cargo test-roms --update      # Record the results of this run in the list of passing tests
cargo test-roms --verify-boot # Run the boot ROM before every test and check the boot cache against it (the nightly CI run does this)
cargo cpu-tests               # Run the JSON CPU tests (every opcode, checked cycle by cycle)
cargo save-states             # Check that the kept save states (save-states/) still load, and that this version stores the fields and variants the newest set lists
cargo save-states --record    # Keep a new set of save states, after a change to the fields or variants save states store

# Iced frontend (desktop app)
cargo play                            # Open a ROM from the toolbar
cargo play path/to/rom.gb             # Run a specific ROM
cargo play path/to/rom.gbc --cgb      # Run in CGB mode
cargo play path/to/rom.gb --model sgb  # Run on another hardware model (dmg-0, dmg, mgb, sgb, sgb2, cgb-0 to cgb-e, agb)
cargo run --release -p nubo -- --measure-efficiency path/to/rom.gb   # Measure the emulator thread's wake-ups, buffers and frames per second (no window), as JSON

# Headless frontend (for screenshots and test verification)
cargo screenshot path/to/rom.gb 5          # Run 5 emulated seconds and capture a screenshot
cargo screenshot path/to/rom.gbc 5 --cgb   # CGB mode
cargo screenshot path/to/rom.gb 5 --model mgb   # Another hardware model

# Benchmark (speed, and fingerprints that show whether a change altered any output)
cargo benchmark ~/Roms/GameBoy                       # Time every game in a folder on DMG and CGB
cargo benchmark ~/Roms/GameBoy --record before.txt   # Record fingerprints of frames, audio and end state
cargo benchmark ~/Roms/GameBoy --compare before.txt  # Check a later build produces exactly the same
cargo benchmark ~/Roms/GameBoy --check-save-states   # Check a save state taken halfway goes on exactly like the run
cargo benchmark ~/Roms/GameBoy --shard 2/4 --record part2.txt   # Only the second of four equal parts of the ROMs
cargo benchmark target/test-roms/v7.0 --seconds 4 --jobs 12 --compare before.txt   # Same for all test ROMs
cargo benchmark target/test-roms/v7.0 --seconds 6 --jobs 12 --check-save-states   # Save states of all test ROMs
cargo run --release -p nubo-benchmark --features nubo-core/eager -- ~/Roms/GameBoy --compare lazy.txt   # Check the lazy shortcuts against running every M-cycle on its own

# Speed next to other emulators (see docs/EMULATOR_COMPARISON.md; Linux and macOS, needs git, a C/C++ compiler, make, RGBDS and CMake)
cargo xtask compare-emulators                  # Time Nubo, SameBoy, Gambatte, mGBA, binjgb and Gearboy on the benchmark games (best of 3 rounds of 30 s)
cargo xtask compare-emulators ~/Roms/GameBoy   # The same on other games
cargo xtask compare-emulators --instructions   # Count the instructions inside each emulator with Valgrind instead (Linux), the same however busy the machine is

# Web version (the Iced frontend built for the browser)
cargo xtask web               # Build it and serve it at http://127.0.0.1:8080
cargo xtask build-web         # Build it into target/web/ (what deploy.yml publishes to GitHub Pages)
cargo xtask build-web --quick # Build it much faster, but bigger and slower to run (what CI checks)

# macOS app bundle, Flatpak and logo
cargo xtask bundle            # Build Nubo.app (release build, Dock icon) into target/bundle/
cargo xtask flatpak           # Build the app as a Flatpak, install it for this user and write target/bundle/Nubo-<version>-linux-<arch>.flatpak (Linux, needs flatpak-builder)
cargo xtask windows           # Build target/bundle/Nubo-<version>-windows-x64-setup.exe and a zip to run without installing (Windows, needs Inno Setup 6)
cargo xtask icon path.png     # Write the logo as a 256 px PNG (images/icon.png in the README)
cargo xtask icon path.svg     # Write the logo as an SVG (images/icon.svg)
cargo xtask icon path.ico     # Write the logo as a Windows icon with every size
cargo xtask licenses folder   # Write LICENSE, NOTICE and the crates' licenses for the desktop app into folder
cargo xtask release-notes v0.2.0   # Check the tag, Cargo.toml and the newest AppStream release agree, and print its notes

# Nightly review (see docs/NIGHTLY_REVIEW.md)
cargo xtask benchmark-roms    # Download the free homebrew games the nightly CI benchmarks into target/benchmark-roms
cargo xtask review-units      # List the parts the nightly review splits the code into

```

## Architecture

### Workspace Layout

The root `Cargo.toml` is a virtual workspace. `default-members` covers only the core crates so `cargo build`/`cargo test` at the root don't build the GUI frontends or the xtask tooling.

- `crates/nubo-core/`: The emulator itself, a plain Rust library with no platform dependencies
- `crates/nubo-logo/`: The logo as a few rounded rectangles, with a small anti-aliased rasterizer, an SVG export and a Windows `.ico` export; used by the Iced frontend (its window icon, and `nubo.exe`'s icon through `build.rs`) and by `cargo xtask bundle`, `flatpak` and `windows`
- `crates/serializable_derive/`: Derive macro for save-state serialization
- `frontends/*`: One crate per frontend, each depending on `nubo-core`
- `xtask/`: Project tasks written in Rust. `cargo xtask web` and `build-web` install the `wasm32-unknown-unknown` target if needed, build `nubo` with the `wasm-release` profile (with `--quick` the much faster `release` profile, which CI checks the browser build with), and generate the JavaScript glue with the `wasm-bindgen-cli-support` library next to `frontends/iced/web/index.html`, so neither wasm-pack nor Node.js is needed. `flatpak` (`flatpak.rs`) writes a manifest (the freedesktop runtime with its Rust SDK extension, and the sandbox's permissions in `FINISH_ARGS`), every crate of `Cargo.lock` as a flatpak-builder source (Flatpak builds are offline; this is what Flathub's flatpak-cargo-generator writes), the SVG icon and the license files to `target/flatpak/`, then builds the working tree with flatpak-builder, installs it for the current user (adding a user Flathub remote for the runtime if needed) and exports it as a single file, `target/bundle/Nubo-<version>-linux-<arch>.flatpak`, that others install by opening it (it points to Flathub for the runtime). The menu entry and the AppStream metainfo live in `frontends/iced/linux/` (`LINUX_FILES`) and are named after `APP_ID` (`io.github.mschoenm.nubo`, also the macOS bundle identifier), which the Iced frontend sets as its window's app id: GNOME on Wayland ignores window icons and shows the icon of the installed menu entry that matches the window. The metainfo's screenshot, `images/flatpak/tobu-tobu-girl-deluxe.png`, is linked by its raw.githubusercontent.com address on `main`, so it only loads while the repository is public; it shows a CC BY 4.0 homebrew game, credited in the description and the README. `windows` (`windows.rs`) builds `nubo` in release mode and puts it with the license files into an Inno Setup installer (`frontends/iced/windows/nubo.iss`: per user, no administrator rights, Start menu entry, uninstaller, optional "Open with" for `.gb`/`.gbc`; its `AppId` must never change) and a zip; `frontends/iced/build.rs` gives `nubo.exe` the logo as its icon (`nubo_logo::ico`) and its file properties with `winresource`, and release builds use the Windows subsystem so no console window opens. Every cargo build xtask runs, the Flatpak's included, gets `NUBO_COMMIT`: the commit of the working tree (with `-dirty` after it when tracked files have uncommitted changes, `GITHUB_SHA` without git), which `nubo_core::BUILD_COMMIT` holds and save states store, so every release and nightly build's states say exactly which build made them; a plain `cargo build` leaves it empty. `bundle`, `flatpak`, `windows` and `build-web` put copies of `LICENSE`, `LICENSE-APACHE` and `NOTICE` (as `.txt`) next to the app, with `THIRD_PARTY_LICENSES.txt` written by `licenses.rs` from `cargo metadata`: the license files of every crate the app is built for that target from, or the standard text of their license for crates that ship none (it fails when a crate has neither). `wasm-bindgen` and `wasm-bindgen-cli-support` are pinned to the same exact version in the root `Cargo.toml` (the Iced crate depends on the pinned `wasm-bindgen` for this) and must be upgraded together `benchmark-roms`, `review-units` and `metrics` serve the nightly review (`docs/NIGHTLY_REVIEW.md`): the first downloads three homebrew games (Tobu Tobu Girl Deluxe, µCity, Geometrix) from the gbdev Homebrew Hub database at pinned commits with checksums; the second splits the Rust code into parts of at most 1,200 lines from the file tree as it is (a module with its folder when it fits, else its file and its children, small neighbours packed together) and picks the one whose least recently reviewed file was reviewed longest ago, remembering dates per file so regrouping loses nothing; the third keeps the metrics log (one JSON object per night) and renders its wiki page, flagging values worse than their 14-night median by more than their threshold. `compare-emulators` (`compare_emulators.rs`, its fetching and building in `compare_emulators/build.rs`) fetches SameBoy, Gambatte (gambatte-core), mGBA, binjgb and Gearboy with git at pinned commits into `target/emulator-comparison`, builds each with its own release flags together with a harness from `xtask/emulator_harnesses/` that runs a ROM the way nubo-benchmark runs it in Nubo (`harness.h`: 44,100 Hz audio in buffers of 512 samples, the same scripted buttons, every frame drawn, only the time inside `run_buffer` counted), and prints a table of each emulator's best round, or with `--instructions` the instructions callgrind counts inside each emulator per emulated second; Nubo runs in nubo-benchmark, also with the `eager` feature. It is the one task that needs C and C++ tools, and leaves out an emulator whose tools are missing. The other emulators are only built and run locally, never distributed or ported from (Gambatte is GPL-2.0-only)

### Core Emulator (crates/nubo-core/src/)

The emulator follows a component-based architecture reflecting real Game Boy hardware:

- **Emulator** (`emulator.rs`): Top-level entry point that owns the CPU and provides the public API. `lib.rs` re-exports everything frontends need from the crate root (`nubo_core::Emulator`, `nubo_core::Model`, ...)
- **Errors** (`error.rs`): `LoadRomError`, `SaveStateError` and `CheatError`, returned by the public API. Input from users (ROMs, zip files, save states, cheat codes) must never make the core panic
- **Save states** (`emulator/save_state.rs`): `NUBO SAVE STATE` and a zero byte, the format version (28), a header of named fields (`SaveStateHeader`: the Nubo version and the commit (`BUILD_COMMIT`) that made it, model, game title and the game's header checksum, which frontends read with `SaveStateHeader::read` to know the model before loading), and then the emulator: `cpu` and the components on the address bus at the top level, named after the hardware (`bus`, `cartridge`, `timers`, `ppu`, `apu`, `oam_dma`, `vram_dma`, `serial`, `speed_switch`, `joypad`; `AddressBus::write_save_state_components`), so moving code between structs doesn't move stored values. Every value is stored with its name (see Serialization System), the same on every platform, so states keep loading in later versions and as far as possible in earlier ones: a value a state doesn't have starts as it does right after power-on (loading first loads the state of a just-started emulator with the same game), values this version doesn't know are skipped, and values it can't read keep their power-on value and are reported (`Emulator::load_state_with_report`). States from before format 28 and from a newer format version are refused with a message saying which, as are another model, another game, another version of the game (the same title with another header checksum) and data that isn't read to the last byte; a failed load leaves the emulator untouched. `FORMAT_VERSION` only changes if the file layout or the way values are stored does. Fields that don't belong in save states (caches, values that are always zero between `Emulator` calls) are marked `#[serializable(skip)]` or left out of a manual impl with a comment. A loaded state must go on exactly like the run it was saved from, which `cargo benchmark --check-save-states` checks. `save-states/` keeps sets of states earlier versions made, which every later version must load without a value it can't read (`frontends/save_state_check`, see Frontends). `a_loaded_state_restores_every_field_of_the_cpu_the_address_bus_the_ppu_and_the_apu` compares every field after loading, so only the fields it lists as left out may differ, and `a_value_a_state_lacks_starts_at_its_power_on_value` checks the power-on values. Left out on purpose: the buttons the player holds (host input), the PPU's hand-over of the finished frame, the samples the APU already made and the sample rate (a state loaded at another rate goes on at the new one)
- **Model** (`model.rs`): The emulated hardware: DMG-0, DMG (A/B/C), MGB, SGB, SGB2, CGB-0/A/B/C/D/E and AGB, chosen when the emulator is made (`Emulator::new(model)`). Variants are ordered like SameBoy's model numbers, so revision checks such as `model <= Model::CgbC` read like SameBoy's. Each model leaves the boot ROM with its own registers (`cpu/post_boot.rs`), DIV phase (also for CGB games, which Mooneye can't check) and frame position (`AddressBus::exit_boot_rom`), calibrated against Mooneye's boot tests, GBMicrotest's poweron tests and Gambatte's display_startstate tests, and the phase of the boot sound on channel 1, calibrated against Gambatte's ch1_init_pos tests. Work RAM powers on with each model's pattern (`power_on_work_ram` in `address_bus.rs`): alternating 256-byte blocks of 0xFF and 0x00 on monochrome models, fixed pseudo-random noise on the CGB. SGB support covers the hardware differences only; SGB palettes and borders are not emulated
- **Clock** (`clock.rs`): How M-cycles (machine cycles, one CPU step), PPU dots and the system counter behind DIV relate, at both speeds (`SYSTEM_COUNTER_TICKS_PER_M_CYCLE`, `dots_per_m_cycle`)
- **CPU** (`cpu.rs`, `cpu/`): Z80-variant processor with registers, interrupts, and instruction execution. Whether it runs, is halted or stopped, what its next fetch does and the IME's state are enums (`RunState`, `NextInstruction`, `InterruptMasterEnable`); HALT with IME on and an interrupt pending pushes HALT's own address, as SameBoy does. STOP with an armed CGB speed switch follows SameBoy (`address_bus/speed_switch.rs`): DIV resets after STOP's second byte, double speed starts 6 clock units later, the PPU and DMA freeze for a few units and the CPU halts for 0x20008 units; the freeze lengths and TIMA's jump ahead at fast TAC speeds are fitted to Gambatte's and AGE's hardware tests. Other STOPs enter STOP mode (`address_bus/stop_mode.rs`, also SameBoy) until a button pulls a joypad line low: the timers, DMA and serial port stand still, monochrome models stop the PPU and show white, and the CGB's PPU keeps running cut off from whatever the CPU could access when STOP started (black outside mode 3)
  - `opcodes.rs`: Main opcode dispatch and execution
  - `microops.rs`: Low-level CPU operations (memory access, timing)
  - `alu.rs`, `bitops.rs`, `loads.rs`, `jumps.rs`: Instruction implementations by category
  - `timers.rs`, `interrupts.rs`: Timer and interrupt handling. While running, interrupts are sampled after the opcode prefetch. HALT spends one more M-cycle fetching the next opcode before it checks for a pending interrupt (and the HALT bug). While halted, the CPU samples once per M-cycle like SameBoy (before the cycle on CGB and on the first halted cycle, mid-cycle on DMG) and finishes that cycle before waking or dispatching
- **AddressBus** (`address_bus.rs`, `address_bus/`): Memory mapping and hardware register access. Its module docs list the order of one M-cycle once, its variants, and what a new per-cycle component has to join (`bulk_cycles_available`). The CPU goes through `cpu_read_byte`/`cpu_write_cycle` (DMA conflicts, write timing, catching the PPU and APU up); `peek`/`poke` are the raw view without side effects, which debug builds only allow once the PPU has caught up. The mode copies other components keep (CGB mode, double speed, the system counter) are only changed through `AddressBus` setters. The `eager` feature runs every M-cycle on its own with nothing left behind
  - `cartridge.rs`: ROM loading, cartridge type detection, and `Cartridge`: the ROM, the header, the RAM, the frontend's effects and a `CartridgeMapper` enum of the controllers, whose registers save states store under the controller's kind (`mbc1`, `mbc3`, ...), so a later version that picks another controller for a cartridge type starts it at power-on instead of misreading them. The address bus passes the time since power-on with each cartridge write (`write_rom_at`, `write_ram_at`); tests use `write_rom`/`write_ram`, which write at power-on
  - `mbc1.rs`, `mbc2.rs`, `mbc3.rs`, `mbc5.rs`, `huc1.rs`: The controllers' registers. Writes to battery-backed RAM and changes of the MBC3 clock only set flags; the emulator passes them to `CartridgeEffects::save_ram`/`save_rtc_state` once at the end of each call that ran the CPU (`Cartridge::report_save_changes` from `Emulator::finish_running`), since some games write the RAM thousands of times a frame and latch the clock every frame. Loading a save state never saves by itself, so it can't overwrite the player's battery save. A save file shorter than the header's RAM size fills the start of the RAM. An MBC3 with more than 2 MiB of ROM or 32 KiB of RAM is an MBC30 (all eight ROM bank bits, eight RAM banks), as in SameBoy; its bank register keeps the four lower bits written (bit 3 picks a clock register on a cartridge with a clock, and banks 4-7 and clock registers 5-7 read 0xFF there), and reads of the clock show its registers as of the last latch, which any write to 0x6000-0x7FFF takes, as CasualPokePlayer's latch-rtc-test and rtc-invalid-banks-test check. The MBC3's real-time clock follows the frontend's wall clock (`CartridgeEffects::current_time_millis`), or with `CartridgeEffects::rtc_clock` returning `RtcClock::EmulatedTime` the PPU dots the address bus counts since power-on (kept in save states), which the test ROM runner uses so clock tests are repeatable
  - `dma.rs`, `hdma.rs`: DMA transfer implementations. While VRAM DMA copies a block, a running OAM DMA copies VRAM DMA's byte instead of its own, to the OAM index given by the low byte of VRAM DMA's source address. OAM DMA holds the bus its source is on, so CPU reads and writes that collide with it go through `cpu_read_byte`/`cpu_write_byte`: reads see the byte just copied and writes land in OAM instead, following SameBoy where Gambatte's hardware tests agree and the tests where they don't. The transfer stands still while the CPU is halted. While it copies it also holds OAM from the PPU, as in SameBoy: OAM scan re-checks the last Y and X it read, mode 3 object reads see the bytes being copied, and STAT shows mode 0 instead of mode 2
  - `write_timing.rs`: CPU writes to PPU registers that land a dot or two off the M-cycle boundary or briefly expose an intermediate value, following SameBoy's access conflict tables. The PPU runs dots ahead of the CPU for these and the debt is paid back on the next M-cycle
  - `cheats.rs`: GameShark/GameGenie cheat code support. Cheats apply in the order they were turned on, and the first that matches an address wins
- **GPU** (`gpu.rs`, `gpu/`): Dot-based PPU. `gpu.rs` runs each line's timeline (LY, the STAT mode and LYC flag as the CPU sees them, the STAT interrupt line, and when the CPU may access OAM and VRAM). Which timing applies is a `TimingVariant` (DMG, CGB, CGB in double speed). Its dot positions are calibrated against the Mooneye PPU tests and an instrumented SameBoy, so change them only together with `cargo test-roms`. The line start (when STAT shows each mode, LY=LYC, the mode 0 and mode 2 interrupt sources, line 153) and the window's WY checks follow Gambatte's timing at both speeds, measured by comparing the CPU's register accesses and interrupt requests in both emulators
  - `pipeline.rs`: Pixel FIFO renderer and OAM scan, ported from SameBoy's mode 3 (Expat License). Fetcher, object fetches and FIFOs advance dot by dot and read registers like SCX, LCDC and the palettes when SameBoy does, so mid-line writes take effect mid-line
  - `plain_pixels.rs` (in `pipeline/`): Nubo's own fast paths for plain pixels and whole tiles, kept apart from the SameBoy port. The chain of `#[inline(always)]` functions there is what specializes them per color source; removing it puts the color choice back into every pixel
  - `stat.rs`: STAT, LY=LYC, the STAT interrupt line and the late CGB writes
  - `access.rs`: When the CPU may reach OAM and VRAM, VBK/OPRI, and the effects of OAM DMA and STOP
  - `steady.rs`: The stretches the PPU runs in bulk (`has_steady_shape`, `run_steady_dots`, `quiet_dots`). The per-dot countdowns live in one `Countdowns` struct, whose `is_idle` the bulk paths check, and `gpu/tests/random_scenes.rs` checks bulk runs against dot by dot on random scenes
  - `save_state.rs`: The PPU's save state, written through a macro that names every field, so a field missing from both the saved and the skipped list doesn't compile; loading checks every value it could index or overflow with (`check_loaded_state`)
  - `palettes.rs`: DMG and CGB palette handling. `DMG_SHADES` are the four grays the core draws original Game Boy games in, which frontends swap for the player's palette
- **APU** (`apu.rs`, `apu/`): Audio processing with four channels. The channel timing and hardware quirks follow SameBoy's APU (MIT licensed), which is what SameSuite verifies, including its differences between hardware revisions (`Apu::set_model`). The PCM12/PCM34 read glitches of CGB-C and older are modelled with a per-M-cycle `pcm_mask`. Channels count 2 MHz ticks (two per M-cycle, one in double speed); the frame sequencer runs on falling edges of DIV bit 4 (bit 5 in double speed), which `AddressBus` reports through `system_counter_changed`, including on DIV writes. Channels are named by the `Channel` and `Square` enums. The output's sample clock keeps its remainder, so exactly the sample rate's worth of samples comes out per emulated second (rates from 1,000 to 1,048,576 Hz; others are clamped). Save states hold the band-limited buffers, the high-pass charges, the last mixed levels and the wave channel's bus address, and loading checks every value a corrupted state could overflow with. The APU's fields are private to `apu/`, so code elsewhere can only reach them through methods that catch up first. Its `Debug` output shows the caught-up APU without the scheduling caches
  - `square.rs`, `sweep.rs`: The two square channels and channel 1's frequency sweep
  - `wave.rs`: Programmable wave channel
  - `noise.rs`: Noise channel and its LFSR, including NR43 write glitches
  - `envelope.rs`: Volume envelopes (`Envelope`) and the NRx2 "zombie mode" glitch
  - `length.rs`: The length counters (`LengthCounter`) the four channels share
  - `blep.rs`: Band-limited synthesis used to turn channel samples into audio
  - `catch_up.rs`: The channels run lazily, like SameBoy's. `Apu::step` only counts M-cycles; they run in one go in the M-cycle that fills the audio buffers (and on each sample after it, so the samples the emulator hands out are complete) and before register accesses (the CPU's reads of sound registers catch up in `cpu_read_byte`), DIV-APU events that change what the channels play and speed switches, and one M-cycle at a time only while channel 1's sweep calculates, a DMG noise trigger is delayed or the wave channel reads the CPU's bus (a stopped wave channel only in the M-cycle its timer runs out). A batch is cut at every M-cycle in which a channel can change its output (each channel's next change stays known between cuts), so every audio sample stays bit-identical to running each M-cycle on its own (checked by the APU unit tests, which compare lazy and bulk runs with running each M-cycle on its own for fixed and random register writes on every model, and by `cargo benchmark --compare`). Debug builds also check that a frame sequencer step judged quiet changed nothing, that cached predictions match fresh ones, and that the mixer's skip test covers everything it reads. `cycles_until_timing_dependent_run` says when the channels must run one M-cycle at a time. `advance_cycles` moves through stretches without DIV-APU edges in one call; the address bus calls it before `system_counter_changed`
- **Joypad** (`joypad.rs`): Input handling. Keyboard keys and controller keys are tracked separately and combined, so releasing one source doesn't release a key the other still holds. Save states keep the button group the game selected and a pending joypad interrupt, not the buttons the player holds
- **Controller** (`controller.rs`): Platform-neutral `ControllerState` (16 buttons including shoulders, triggers and stick clicks, plus the left stick, positive = right/up) and `ControllerMapping` (controller buttons to Game Boy keys, stick to D-pad with a dead zone; `ControllerMapping::empty()` for fully custom mappings). Frontends read the hardware and call `Emulator::set_controller_state()`
- **Serial** (`serial.rs`): Serial port emulation. The internal clock is SameBoy's flip-flop, toggled by falling edges of a system counter bit (bit 7, or bit 2 with the CGB's fast clock) and pulled low by SC writes, so transfers keep their phase across DIV and SC writes
- **BIOS** (`bios.rs`): The boot ROMs' bytes. Their sources (`nubo_dmg.asm`, based on Bootix, and `nubo_cgb.asm`, based on SameBoy's) are in `crates/nubo-core/boot_roms/`, built with RGBDS by `build.sh` (see its README). Both show the Nubo cloud and name and keep the timing and end state of the boot ROMs they replaced to the cycle, because the post-boot calibration depends on it. Besides 0x0000-0x00FF, the address bus maps them from 0x0200 to their end (0x08FF for DMG, 0x0BFF for CGB) while they run
- **ROM archives** (`rom_archive.rs`): `Emulator::load_rom` accepts zip files and loads the first `.gb`/`.gbc` entry. Uses the `zip` crate with only the pure-Rust zlib-rs deflate backend so the core still builds for wasm32 without C dependencies

### Serialization System

The project uses a custom `Serializable` trait with a derive macro (`crates/serializable_derive/`) for save states. Every struct is stored as its fields, each with its name and length (`FieldWriter` and `read_fields` in `serializable.rs`, which hand-written impls use too), and enum variants by name, so players never lose a save state to an update. Stored names are permanent and a stored value means the same in every version, so: adding a field needs nothing (other versions leave it at its power-on value or skip it); removing or reordering fields needs nothing; renaming a field or variant in the code keeps its stored name with `#[serializable(name = "stored_name")]` (change a stored name only when it would mislead about what the value is now); and a field whose type or meaning changes (another size, other units, other values) is stored under a new name. A value that can't be read from its bytes keeps its power-on value and the rest still loads; only damaged data and values a component's checks reject fail a load. Values are little-endian and fixed-size (never `usize`), floats as their IEEE 754 bits, so a state made on one platform loads on every other. `cargo test` and `cargo save-states` fail when what save states store changes (`Emulator::save_state_layout`: every field with how its value is stored, such as `ppu.lcdc: u8` (`Serializable::encoding`), and every variant each enum value can be stored as, which the derive and `write_variant` report, against the newest kept set's `layout.txt`), listing the added and removed entries: keep the stored name of a field or variant only renamed in the code, store a field whose type changed under a new name, and otherwise keep a new set with `cargo save-states --record` in the same pull request.

### Frontends

- **Iced** (`frontends/iced/`): Desktop app built with Iced. Emulation runs on its own thread paced by the cpal audio queue (`emulation/thread.rs`'s `EmulatorThread`; what both builds share is in `emulation.rs`: `Machine` carries out each `Command`, and a session starts with the player's `Playback` of pause, fast forward and volume, so nothing plays before they apply): it sleeps until the sound card's callback wakes it as the queue runs low, or a command from the UI wakes it, and never polls. It tells the UI about each new frame through a subscription (`Session::new_frames`), skipping frames identical to the one before, so the window redraws for new pictures instead of on every refresh of the screen (not at all on still screens): about 60 times a second at normal speed on any screen, more when fast forwarding (the extra audio buffers are spread over the time one buffer plays, so their frames arrive evenly and fast screens can show them). The browser build keeps `window::frames()`, since its emulation runs on those ticks. Whatever changes with time alone (toasts expiring, the fullscreen bar hiding, problems reported from other threads) is checked by `ticks::every` (`App::check_interval`: four times a second while toasts or the bar need it, once a second while a game runs), since nothing else redraws a still screen. Each session's frame subscription is keyed by a session number, not an address, so a restarted game always gets a new one. While the game is paused the desktop build also pauses the sound stream, and `Game::apply` only sends pause, speed and volume when they change, since every command wakes the emulator thread. Battery-backed RAM and RTC state are persisted by `battery.rs` as `<rom name>.sav` and `<rom name>.rtc` in the per-user data folder picked by the `directories` crate (`~/Library/Application Support/Nubo/saves` on macOS, `%APPDATA%\Nubo\data\saves` on Windows, `$XDG_DATA_HOME/nubo/saves` on Linux), written once the game's save writes have settled for 250 ms (at most 1 s after the first one), when the game pauses and when the session ends. Iced 0.14 has no hook for quitting, so on macOS Cmd+Q and Dock > Quit probably end the app without `stop_game` (unverified): battery saves are on disk by then, but the Resume slot and thumbnail aren't written. Controllers are read with gilrs on a thread of their own that blocks until a controller reports something, with gilrs's force feedback off (`controllers.rs`, on every frame in the browser build) and reach the app as a subscription, so they work on every screen; the app forwards their state to the emulator thread, hiding buttons pressed while the game isn't running until they are released (`menu_presses.rs`), so the A that picks "Resume" doesn't reach the game. gilrs's Windows backend polls every 8 ms on its own thread whatever the app does. The player binds one key and one controller button per Game Boy button and shortcut (`controls.rs`, saved in `settings.toml`); Game Boy buttons go to the core as a `ControllerMapping`, shortcuts such as the pause menu are handled by the app. `app.rs` routes between the library screen and the game screen (`views/`); its messages come in groups (`GameMessage`, `LibraryMessage`, `SettingsMessage`, `WindowMessage`), each handled in its own file under `app/` (`playing.rs`, `library_screen.rs`, `settings_window.rs`, `window_events.rs`, and `player_input.rs` for keys and controllers), and after every message the game is told whether to run, how fast and how loud (`Game::apply` only sends what changed), with the settings window, drop target and toasts layered on top; widget styles and the light/dark themes live in `ui/` (icons are Lucide, via the `lucide-icons` font). Settings are saved as `settings.toml` in the config folder (`settings.rs`). The library (`library.rs`) scans the user's ROM folders in the background with `Emulator::read_rom_header`, caches what it found in `library.toml` and keeps a PNG of each game's last screen in `thumbnails/`, both in the data folder. At startup a quick check (`scan::check`, existence only) forgets games whose file was deleted before the full scan runs. A game whose library folder (or, outside the folders, whose own folder) is gone, such as on an unplugged drive, is kept but hidden as unavailable, so it comes back intact. `library/watcher.rs` watches the folders with `notify-debouncer-mini` (one second of quiet before reporting, ROMs and folders only) and rescans on changes; the Rescan buttons, the watcher and folder changes all go through `App::rescan`, and only one scan runs at a time, with requests during it leading to one more scan after it. Title screens and box art saved after the ROM last changed are reused instead of being made again. Problems on the emulator thread go through `notices.rs` to toasts instead of only stderr. `game.rs` holds the running game and its overlay state (auto-hiding top bar, pause menu, fast forward); the emulator thread runs `speed` audio buffers per played one to fast forward. The picture (`Screen`) is copied once per new frame, and a copy as the emulator drew it is only kept while an original Game Boy game is shown in a palette other than gray. On Windows a minimized window reports a zero size and stops taking frames while the game plays on; macOS and Linux give no such signal. Save states (`save_states.rs`) live in `states/<rom file name>/` in the data folder as `<slot>.state` plus a `<slot>.png`; with "Continue games where you left off" on (off by default, Settings > Playing), the `resume` slot is written when a game stops and loaded when it starts again. A `.state` file is exactly the core's save state; the model comes from its header. A state that can't be loaded is renamed to `<slot>.kept-<number>.state` (and its picture with it), so the next save to the slot, such as the `resume` slot when the game stops, can't overwrite it. Screenshots go to `Pictures/Nubo` (`screenshots.rs`). The logo (a pixel buddy puffed into a cloud, on a purple rounded square) is defined once as rounded rectangles in `crates/nubo-logo`; the app draws it with a canvas in its theme's accent (`ui/logo.rs`), renders it as the window icon, and `cargo xtask bundle` renders it into the `.icns` of `Nubo.app` (macOS only, using `iconutil`, signed ad hoc). Library cards show each game's title screen, captured by `title_screens.rs`: after a scan, games without one are run for 10 emulated seconds with no window or sound (about half a second each, two at a time) and the frame with the most detail is kept in `title_screens/` in the data folder. With "Download box art" on (on by default, Settings > Library), `box_art.rs` also looks up each game in the libretro thumbnail collection, four at a time with `ureq`: by file name, then through the No-Intro game lists from the libretro database (downloaded once to `box_art/lists`) by file name and CRC32. Pictures are shrunk to 256 px and kept in `box_art/`; a failed download stops the queue until the next scan. Cards show box art, then the title screen, then the last screen played. Slow work (scans, title screen captures, box art lookups, reading the game lists and decoding saved pictures) runs on threads of its own through `background::run` (a thread that can't start or work that panics comes back as an error, so no job slot stays taken), never on Iced's shared task pool or the UI thread, and pictures reach the view already decoded (`Library::load_pictures` loads the one picture each card shows); the game lists are only read when a game still needs its box art looked up. Card pictures are drawn at a whole-number scale on a dark frame, and DMG pictures use the chosen palette. Cheats are kept per game in `cheats/<rom file name>.toml` (`cheats.rs`) and sent to the emulator thread when they change. DMG palettes (`palettes.rs`) are applied by the frontend, which swaps the four grays of DMG frames (`nubo_core::DMG_SHADES`) for the chosen colors, so the core always draws gray. The bound D-pad, A, B, Start and Select keys and buttons also move through the library, the pause menu and the settings window (`App::navigate`); the settings rows the D-pad visits are listed by `views::settings::rows`, in the order the page shows them, and the view outlines the focused one; the library's column count and card positions are worked out in `views/library.rs` to match Iced's grid, so the selected card can be scrolled into view. It also builds for wasm32 (`cargo xtask web`), which `deploy.yml` publishes to GitHub Pages on every push to main that passes CI: there `emulation/web.rs` replaces the emulator thread and emulates the frames due on each frame tick, one whole frame at a time (the browser's sound takes 2,048 samples at a time, so filling the queue whenever it ran low emulated frames in bursts and showed only the last of each). `emulation/pacing.rs` decides how many are due: on screens within 1% of 60, 120 or 240 Hz frames are locked to the refreshes (one every 1, 2 or 4, or two per refresh when a browser saving power draws 30 times a second), counted from the `requestAnimationFrame` timestamps `web/refresh_clock.rs` records (Iced's ticks reach the app milliseconds later by varying amounts), so the game runs about 0.45% fast there; on other screens they go by the average time between ticks. The audio queue, sized from the sound buffer cpal reports, never changes when a frame runs: `SampleRateControl` keeps its average length at its target by setting the emulator's sample rate up to 1% off (besides making up for a locked game's speed), ROMs are read as bytes through rfd's browser file picker, and battery saves go to localStorage (`battery/local_storage_slot.rs`, keyed by ROM file name) instead of files (`battery/file_slot.rs`), flushed as soon as a burst of save writes settles. The browser has no system fonts, so the browser build only has the Fira Sans that Iced bundles; text that sets a font must use `theme::BODY_FONT` or `theme::HEADING_FONT`, never `Font::DEFAULT`, or it draws nothing there. Code the browser build shares must take `Instant`, `SystemTime` and `Duration` from `iced::time`, since std's panic on wasm32-unknown-unknown. The library, save states, cheats, screenshots and box art are desktop only (each module has an `AVAILABLE` flag). `efficiency.rs` (desktop only, `nubo --measure-efficiency <rom>`) plays a game without a window or sound while playing, paused, fast forwarding and on a still screen, and prints the emulator thread's wake-ups, audio buffers and frames per second as JSON (`Session::activity` counts them), keeping battery saves in a temporary folder; the nightly metrics track it as the battery cost
- **Headless** (`frontends/headless/`): No-display frontend for running ROMs and capturing screenshots. It runs the given number of emulated seconds with a real-time clock that counts emulated time, so two runs give the same PNG
- **Benchmark** (`frontends/benchmark/`): Runs ROMs (files or folders) on each chosen model for a fixed stretch of emulated time with scripted button presses, and reports the speed as emulated time per second spent inside the core (20x real time is the minimum target on both DMG and CGB). It also hashes every frame, every audio sample and the final save state; `--record` writes these fingerprints and `--compare` checks a later build against them, so an optimization can be shown to change nothing at all, across the games and all test ROMs, beyond what the test ROMs' pass/fail results show. `--shard 2/6` runs only the second of six equal parts of the ROMs (every sixth, so each folder is spread over all parts), which the nightly CI uses to split its checks over several machines
- **Save state check** (`frontends/save_state_check/`): Keeps players' save states loading across updates. `save-states/<date>/` holds sets of states made by the version of that day, of six test cartridges the tool builds itself (`cartridges.rs`: one per memory bank controller, each setting up the sound, timer, serial port, objects, window and OAM DMA, and on the CGB its palettes, banks, VRAM DMA and double speed; pinned by `the_cartridges_never_change`, since a state only loads into the cartridge it was made with) and of the three games of `cargo xtask benchmark-roms` 20 seconds in, with `layout.txt` listing every field that version stores with how its value is stored and every variant each enum value can be stored as. Which fields a state stores depends only on the cartridge's controller, and every variant is listed whichever one a state holds, as are the fields of an empty `Vec`'s items and of a `None`, so the test cartridges cover the whole layout. `cargo save-states` loads every kept state with `load_state_with_report`, fails on any value it can't read, plays each on for 2 seconds, and fails when this version's layout isn't the one the newest set lists; `cargo test` does the same for the test cartridges' states without the games, which the nightly CI runs on Linux, macOS and Windows, so states made on one platform are shown to load on the others. `--record` adds a set named after today's date (UTC) only when the layout changed. Sets are never changed or removed, and a game whose states are kept must stay in `benchmark_roms.rs` at the same version (states of another version of a game don't load)
- **JSON Test Runner** (`frontends/json_test_runner/`): Runs the v2 tests of [adtennant/GameboyCPUTests](https://github.com/adtennant/GameboyCPUTests) in parallel, checking registers, the number of M-cycles, bus activity on every M-cycle and the final RAM. A missing or empty test folder, or a file whose test run panics, counts as a failure. The 241 files are downloaded at a pinned commit into `target/json-cpu-tests/` and checked against `v2.sha256`; pass a directory to use a local copy instead. The emulator runs in `processor_test_mode` (flat 64 KB RAM) for these tests
- **Test ROM Runner** (`frontends/test_rom_runner/`): Downloads a pinned, checksummed release of [c-sp/game-boy-test-roms](https://github.com/c-sp/game-boy-test-roms) into `target/test-roms/`, plus daid's and CasualPokePlayer's tests from the [GB Emulator Shootout](https://github.com/gbdev/GBEmulatorShootout) at a pinned commit (the files listed with their checksums in `shootout.sha256`), and runs Blargg, Mooneye (Gekkio's and Wilbert Pol's), SameSuite, dmg-acid2, cgb-acid2, cgb-acid-hell, Mealybug Tearoom, Gambatte, GBMicrotest, AGE, rtc3test, Bully, Strikethrough, Scribbltests, TurtleTests, little-things-gb, the MBC3 Tester and the shootout tests in parallel (the README lists what isn't run and why), on the hardware models named by each ROM's suffix (Mooneye's G/S/C/A groups and revision lists such as `cgb0BC`, several in a row for AGE such as `-dmgC-cgbBCE`, where `ncm` is a CGB running a DMG game; DMG and CGB-E when there is none) and each Mealybug test on every revision with a reference image (DMG-blob on DMG, CGB-C, CGB-D on CGB-D and CGB-E). Register-based tests pass when B, C, D, E, H, L hold 3, 5, 8, 13, 21, 34 (and fail on 0x42); screenshot tests pass when the normalized frame matches the reference PNG exactly. Gambatte's tests run on DMG and CGB-C and are checked 15 frames after the boot ROM like Gambatte's own runner (`gambatte.rs`): the hexadecimal number after `_out` in the file name must be drawn in the top-left corner, `_outaudio0`/`_outaudio1` mean silence or sound in the last frame, and the rest match a PNG in Gambatte's colors. Gambatte's CGB color formula is GPL-2.0-only, so the few non-gray colors Nubo draws in those tests map to RGB through a small table learned from the reference PNGs (an unknown color never matches). GBMicrotest writes 0x01 (pass) or 0xFF (fail) to 0xFF82; the ROMs that never write there (test benches and experiments) are skipped. rtc3test's three subtests are picked from its menu by pressing buttons after the boot ROM (each `TestCase` can list `input` keys, and the `subtest` name is added to the ID), and the runner's cartridge hooks make the MBC3 clock count emulated time. The smaller screenshot tests are listed in `SCREENSHOT_TESTS`; Bully runs on CGB only, since real DMGs fail it too, and firstwhite must show its reference in every frame after the game first turns the screen off (`Check::EveryFrame`), since failing emulators flash text for one frame. Register tests also end when the CPU locks up on an undefined opcode, which is how Wilbert Pol's older Mooneye tests finish (`Emulator::is_locked_up`). The shootout tests and Mooneye's MGB madness test run on the model they target and are checked one second after the boot ROM against one of their screenshots, in grayscale with the shootout's tolerance (`Check::GrayscaleScreen`), because those screenshots come from several emulators or use Mooneye's own grays. Tests start where the boot ROM hands over to the cartridge (`boot.rs`): each worker thread runs the boot ROM once per model and set of header bytes it can see (`Emulator::boot_rom_input`) and starts the other ROMs from a copy (`Emulator::clone_with_rom`), with the timeout still counted from power-on. `--verify-boot` runs the real boot ROM for every test instead and fails any test whose copy would have differed, comparing the whole emulator's `Debug` output; the core test `clone_with_rom_matches_a_real_boot` checks the same for every model with ROMs that differ everywhere outside those header bytes. Timeouts count emulated time (each test's `Deadline`: seconds from power-on, seconds after the boot ROM, or frames after it), so results don't depend on how fast or busy the machine is (the whole suite normally finishes in about 30 seconds, or about two and a half minutes with `--verify-boot`). Hangs are caught three ways, so one never holds up the run for more than a few minutes: a test whose emulated time stops advancing (one audio buffer taking over 60 seconds of real time, `STALL_LIMIT`) fails, the run stops once 3 tests have stalled, and a watchdog ends the process if a test makes no progress for 90 seconds because it is stuck inside the emulator. Each test's outcome is stored as it finishes, so a worker that panics only fails the test it was on. Tests are started longest timeout first (`TestCase::longest_run_seconds`), so slow ones such as rtc3test and Blargg overlap with the thousands of short ones

## Key Design Patterns

- **Cycle-accurate timing**: The CPU's `step()` function advances one instruction with proper timing propagated through all components
- **Lazy components, exact results**: Running every component every M-cycle is slow, so the PPU and APU are left behind while nothing they do can be seen, and catch up in one go; the result must be bit for bit what stepping them one M-cycle at a time gives (checked with `cargo benchmark --compare`). The address bus owes the PPU dots (`ppu_owed_dots`) up to the quiet stretch `Gpu::run_dots` reports (no frame, HBlank DMA signal or interrupt request the CPU could act on can come from it: STAT requests only count while IE enables them, until the next VBlank when no STAT source is enabled), and catches it up before any CPU access to PPU state, IF or IE (`reaches_ppu`), around OAM DMA, speed switches, entering and leaving STOP and the boot ROM exit (in STOP mode itself it is left behind like in any other M-cycle); CPU writes to PPU state run their M-cycle dot by dot so `write_timing.rs` stays exact, and save states hold the caught-up PPU. Within a catch-up the PPU runs steady stretches in bulk (`has_steady_shape`: HBlank and VBlank skip ahead, OAM scan goes entry by entry, mode 3 draws plain pixels and whole tiles without its phase machine) and everything else dot by dot. `address_bus/bulk_cycles.rs` runs whole stretches of M-cycles at once (timers and the serial clock count edges of their counter bits, and the APU moves on with `Apu::advance_cycles` up to the next DIV-APU edge): while the CPU is halted and nothing can wake it, and while it runs, for the plain M-cycles (`AddressBus::sync`) in which it only reads ROM or uses work RAM and HRAM, which only count until something else happens (another access, an M-cycle that isn't plain, HALT, STOP, the end of each `Emulator` call). Any new way for the CPU or another component to see or change the hardware's state must run the waiting M-cycles and catch the PPU and APU up first
- **Audio sync**: `step_until_next_audio_buffer()` runs until the APU buffer is full, providing the main emulation loop timing
- **Pull-based rendering**: At vblank the GPU copies the finished frame into a completed-frame buffer. Frontends read it with `Emulator::frame_buffer()` (latest frame) or `Emulator::take_frame()` (returns `Some` once per new frame)
- **CGB mode**: Enabled by the CGB and AGB models, affects memory banking, palettes, and speed switching

## Style Guidelines

- **No `unsafe` code.** The workspace lints forbid it in every crate.
- **Keep clippy clean.** The workspace enables clippy's default lints plus a curated set of pedantic ones in the root `Cargo.toml`; every crate opts in with `[lints] workspace = true`. If a lint must be silenced, use `#[expect(clippy::..., reason = "...")]` on the smallest item possible.
- **Doc comments on types and functions.** Give every struct, enum, trait and non-trivial function a short `///` comment that a junior programmer can follow: say what it is for and explain Game Boy terms (such as "M-cycle" or "MBC") in plain words. Skip doc comments that only repeat the name, such as on simple getters.
- **Few inline comments.** Code should explain itself through clear names and structure; use `//` comments only for things the code can't say, such as hardware quirks or links to the reference they were ported from.
- **Name things after what they are.** Use whole words over abbreviations, treat acronyms as words in type names (`RtcState`, `Mbc1CartridgeMapper`), and don't prefix getters with `get_`. Hardware register names from Pan Docs (`lcdc`, `nr52`, `svbk`) are fine.
- **Define modules at the bottom of the file**, not the top.
- **Newest stable versions.** Rust (the `stable` channel), crates, GitHub Actions (pinned to commits, which Dependabot moves to each release), and tools such as cargo-deny and Flathub's linter all follow their newest stable release, and never a pre-release unless nothing else works. When an update breaks something, the nightly run fails, and that is where it gets fixed. The exception is what others build from Nubo's source: the Flatpak is built with exactly what Flathub would build it with (Flathub's newest freedesktop runtime, its SDK's Rust and `Cargo.lock`), and its build fails when either moves on. Test data (the test ROMs, the benchmark games and the emulators compared against) stays pinned, since results and kept save states depend on its exact content.
- **Credit ported code.** When code, tables or data are ported from another project, say so in a comment at the top of the file with the project's link and license (SameBoy-derived files point to the Expat notice in `apu.rs`), and add the project to `NOTICE` and the Credits section of the README. Only port code, and only add dependencies, under licenses compatible with GPLv3 (MIT, BSD, ISC, Zlib, Apache-2.0, MPL-2.0 and the like; not GPL-2.0-only). Gambatte is GPL-2.0-only: use it only as a reference (its test ROMs, traces of a local build, what it does), implement what you learn in Nubo's own model, and never port its code or tables.

## Verifying Emulator Behavior with Test ROMs

`cargo test-roms` runs every test ROM suite in about 30 seconds (pass a filter such as `gambatte/oamdma` to run part of it) and compares the results with `frontends/test_rom_runner/passing.txt`. It exits with an error both when a listed test stops passing and when an unlisted test starts passing, so after fixing an accuracy issue run `cargo test-roms --update` and commit the updated list. CI (`.github/workflows/ci.yml`) runs it, together with `cargo cpu-tests` and `cargo save-states` (with the games cached), on every pull request and push to main, next to `cargo fmt --check`, both clippy runs above and `cargo doc` with warnings as errors, `cargo deny check licenses bans sources` (`deny.toml` allows only GPLv3-compatible licenses), `cargo test --workspace` on Linux and `cargo xtask build-web --quick`. Pull requests should get their answer in a minute or two, so every CI job is meant to take about a minute, and anything slower goes in the nightly workflow, which every release runs too: a problem may reach main, but never a release. A push to main that passes CI is built with the optimized `wasm-release` profile and published to GitHub Pages (`.github/workflows/deploy.yml`, a workflow of its own so pull requests don't list a deploy job that is always skipped for them). Branch protection only requires the "CI passed" job, which needs all the others. The slow checks run nightly (`.github/workflows/nightly.yml`, at 22:17 UTC), together with CI itself, so whatever a new release of Rust or another dependency breaks shows up that night: `cargo test --workspace` on macOS and Windows, `cargo test-roms --verify-boot`, `cargo benchmark --check-save-states` and the lazy-against-`eager` fingerprint comparison on all test ROMs (both split over several machines with `--shard`, from one build of the benchmark), `cargo deny check advisories`, the Flatpak build for x86_64 and ARM (`.github/workflows/flatpak.yml`, which plays a game in the installed Flatpak with `--measure-efficiency`, since the Flatpak is what Linux users get and nothing else runs it, and runs the newest Flathub linter on the AppStream file, unpinned so a nightly run fails as soon as Nubo couldn't be published on Flathub) and the Windows installer and zip (`.github/workflows/windows.yml`, which plays a game from the unpacked zip and from an installed Nubo, and uninstalls it again), both of which also run on pull requests that change how they are built or `Cargo.lock`, without holding them up. Its `metrics` job starts once every other job has finished, so nothing else of the run is busy while it measures and every night is measured alike (only the checks are split over machines). It measures speed on the homebrew games of `cargo xtask benchmark-roms`, instructions per emulated second under cachegrind (steadier than time on shared machines), the efficiency harness and the build sizes, and writes them with every job's result to the repository's wiki (`metrics.jsonl` and the "Nightly metrics" page) together with the part the nightly review reads tonight. Only scheduled runs write to the wiki, since the rotation counts the changes since the last run that did: a run started by hand would hide the day's changes from the review. Pushing to the wiki needs the `WIKI_TOKEN` secret; runs that don't push keep the files as their artifact. At 02:07 Amsterdam time a Claude cloud routine follows `docs/NIGHTLY_REVIEW.md`: it reviews the day's changes and that part, fixes what is clearly better as long as every fingerprint stays the same, and opens a `claude/nightly-<date>` pull request, or an issue when something regressed. Releases run the nightly workflow, CI included (see Making a Release). When a scheduled or hand-started nightly run passes and `main` has changed since the last one, `.github/workflows/nightly-build.yml` publishes its Flatpaks and Windows installer and zip as the `nightly` pre-release (named like `Nubo-nightly-<date>-linux-x86_64.flatpak` and `Nubo-nightly-<date>-windows-x64-setup.exe`), replacing the one before; it is the same app as the releases, so installing it with `--reinstall` replaces the installed version. Rust follows the stable channel (`rust-toolchain.toml`), and Dependabot proposes new crates and actions (pinned to commits) every day. The Flatpak is built with the freedesktop SDK's Rust instead, as Flathub builds it, which can lag behind, so `rust-version` in the root `Cargo.toml` is that version for the crates the app is built from: clippy then rejects newer standard library items in pull requests. The Flatpak build prints the SDK's Rust and fails when it isn't `rust-version`, and fails when Flathub has a newer freedesktop runtime than `RUNTIME_VERSION` in `xtask/src/flatpak.rs`; both are then raised by hand.

`frontends/test_rom_runner/FAILING_TESTS.md` explains every test that still fails, what was tried and what to try next; keep it up to date when a fix makes one of them pass. `docs/ACCURACY_PLAN.md` is the plan towards claiming to be the most accurate emulator (comparison with other emulators, hardware checks, missing hardware); update it when a phase moves on. Use `--verbose` to see why each test fails. Failing screenshot tests write the emulator's screen and a `.diff.png` (the reference with differing pixels in red) to `target/test-roms/failures/<model>/`.

## Making a Release

Release notes are written once, in the `<releases>` list of `frontends/iced/linux/io.github.mschoenm.nubo.metainfo.xml`, which Linux software centers and Flathub show; CI checks that its newest entry is the version in the root `Cargo.toml`.

1. In a pull request, set `version` under `[workspace.package]` in the root `Cargo.toml` (every crate shares it; run `cargo build` to update `Cargo.lock`) and add a `<release version="..." date="YYYY-MM-DD">` with a `<description>` at the top of `<releases>`, dated the day of the release. Put the output of `cargo xtask release-notes v<version>` in the pull request's description: it shows the notes exactly as the GitHub release will, and the pull request is where they are read over, since the release is published without a draft.
2. Once the maintainer has read the full release text and said to go ahead, merge it, then tag `main` and push the tag: `git tag v0.2.0 origin/main && git push origin v0.2.0`. When Claude prepares a release, it shows the maintainer the whole output of `cargo xtask release-notes` in the conversation, the Install section included, not only the AppStream entry, and waits for their go before merging and tagging. Claude's cloud sessions can't push tags (GitHub answers 403), so they start the Release workflow by hand instead, with the version as its input (Actions > Release > Run workflow): it releases `main` as it is then, after checking that the tag is new, and makes the tag itself when it publishes.
3. `.github/workflows/release.yml` checks the tag against the version, runs the nightly workflow (CI and the nightly checks: `--verify-boot`, save states, the `eager` comparison, advisories), builds the Flatpaks for x86_64 and ARM and the Windows installer and zip, and publishes the GitHub release with them, in about 12 minutes (the Flatpak build is the slowest part). The release's files have no version in their names (`Nubo-linux-<arch>.flatpak`, `Nubo-windows-x64-setup.exe`, `Nubo-windows-x64.zip`), so the README's Download section can link to them in the latest release. If a check fails, nothing is published: once the fix is merged, move the tag to it (`git tag -f v0.2.0 origin/main && git push -f origin v0.2.0`) to run it again, or start a release that was started by hand again, since it only makes its tag once every check has passed (if publishing itself failed after that, re-run its failed jobs instead). The notes of a published release can still be edited on the Releases page.
