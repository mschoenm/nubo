# Iced frontend (`nubo`)

The app players use: a desktop app built with Iced, which also builds for the browser. Each module's docs explain that module; this guide explains how they fit together.

```bash
cargo play [rom] [--cgb | --model cgb-c]   # Run it
cargo play rom.gb --scale 1 --fresh --speed 4 --raw-screen   # As the GB Emulator Shootout runs it (command_line.rs)
cargo play --help                     # Every option
cargo test -p nubo                    # Its tests (not a default workspace member)
cargo clippy -p nubo --target wasm32-unknown-unknown   # Lint the browser-only files too
cargo xtask web                       # Build the browser version and serve it at http://127.0.0.1:8080
cargo run --release -p nubo -- measure-efficiency rom.gb   # Wake-ups, audio buffers and frames per second as JSON (efficiency.rs)
cargo play rom.gb --record-scenes folder   # Ctrl+F12 saves the moment on screen as a scene (app/scenes.rs)
cargo run --release -p nubo -- capture <scene> --games <folder> --home <folder> --output shot.png   # Show a scene and save a picture of the window (cargo xtask screenshots runs it)
```

## How It Runs

- **The game runs in `nubo_frontend::session`.** The window's `Game` (`game.rs`) holds a `GameSession` (the game itself: playback, cheats, palette, save state slots and the picture on screen) and what the window draws over it: the auto-hiding bar, the pause menu (which works like a context menu: Esc or a right click on the game opens it, and a click on the game outside it or a row that leaves it behind closes it, while the bar's buttons work as usual, see `views/game.rs`; its Super Game Boy page is `views/game/sgb.rs`, which changes the paused game's colors and border through `GameSession` and shows the new frame the emulator draws for it; the choices are settings, applied whenever a game starts, since save states don't keep them) and the cheat being typed. Under the `GameSession`, the emulator has a thread of its own on the desktop (`session/sound_card.rs` in `nubo-frontend`), paced by the sound card: it sleeps until the audio callback says the queue runs low or the app sends a `Command`, and never polls.
- **The window only redraws for new pictures.** The emulator thread calls back for each new, different frame, and for the first frame like the one before it, so frame blending settles (`FrameListener::listen`); the callback `subscriptions::new_frames` passes in only tries to send into a channel that holds one message, which its subscription reads, so it never blocks and a still screen draws nothing. What changes with time alone (toasts, the fullscreen bar) is checked by `ticks::every`.
- **This crate is only UI**: the views (`views/`), styles and widgets (`ui/`), the app and its messages (`app.rs` and `app/`), `main.rs`, input translation (`input.rs`, which maps Iced's key codes to `nubo_frontend::controls::KeyCode`, and `menu_presses.rs`), subscriptions (`subscriptions.rs` and `ticks.rs`) and the overlay (`game.rs`), the dialogs that ask the player something (`dialog.rs`, worked out in `app/dialogs.rs` and drawn by `views/dialog.rs`), plus the file dialogs (`rom_picker.rs`, with rfd), its own settings (`settings.rs`, see Where Things Are Kept) and the efficiency harness (`efficiency.rs`). Everything else is in `crates/nubo-frontend`: what the app keeps between runs, the game library, running a game (`session`) and the controllers (`gamepads`). It reports through `futures` channels and callbacks (the frames, the controllers, the library's folder watcher), which `subscriptions.rs` turns into subscriptions, uses `nubo_frontend::time` for clocks and `nubo_frontend::picture::Picture` for pictures (drawn with one cached image handle each, `ui/pictures.rs`, so a picture is uploaded to the graphics card only once).
- **The command line** (`command_line.rs`, read with clap on the desktop only; the browser build has none and starts with `Options::default()`) can start the app for test harnesses such as the GB Emulator Shootout's, and runs the efficiency harness with its `measure-efficiency` command, which `--help` leaves out. With `--scale` the window shows only the game's picture (`views::game::screen_only`): the Game Boy screen, or on a Super Game Boy the 256×224 picture with its border unless the settings hide it, sized to exact display pixels once it opens (`app::screen_only_size`), and only the Game Boy's buttons and fast forward work. With `--fresh` the app reads and writes nothing kept between runs: default settings that aren't saved, no library, battery saves discarded with the cartridge clock on emulated time (`nubo_frontend::session::Saves::Discarded`), and no save states, cheats or screenshots (`Game::keeps_data`). Either one prints toasts on stderr instead (`Toasts::printed`). With `--raw-screen` games show the Game Boy screen as the emulator draws it, whatever palette and screen effects the settings pick (`App::screen_look`, `ScreenLook::RAW`) and a Super Game Boy game's own colors (`App::sgb_player_palette`); the Super Game Boy border still follows its setting, so the Shootout judges the emulation while players keep the original screen look on by default; every palette or screen effect goes through `ScreenLook`, so the flag covers new ones too.
- **Scenes make the documentation's screenshots** (`app/scenes.rs`, desktop only; see `docs/SCREENSHOTS_PLAN.md`). The hidden `capture` command keeps its settings and data in the folder `--home` names (`nubo_frontend::storage::files::use_folder`), so it shows the whole app as players see it (save states, cheats and screenshots included) without touching the player's data, starts the scene's game paused, loads its state and runs its frames (`GameSession::run_frames`), and then saves a picture of the window or prints `ready`. A scene holds the game still (`App::held_for_scene`): it never runs on its own, and the mouse doesn't bring up the fullscreen bar. Toasts are printed instead of shown, and a scene's settings answer the box art and update questions, so nothing covers the picture. `--record-scenes` makes Ctrl+F12 save the moment on screen as a scene, with the light or dark look on screen rather than "System", and a preview taken once the window is drawn again without its toasts; nothing is recorded while a question is open or while the player's own data shows (box art, a last screen played on a library card, the game folders on the Library settings tab, a cheat that is on, or a pause menu page listing saved states or cheats), which scenes don't keep, or while the library is still finding its games or holds a search; held buttons are let go and the library, settings and pause menu scroll back to the top first, as a capture starts. A scene's game keeps no battery saves, with its cartridge clock on emulated time.
- **Every command wakes the emulator thread**, so `GameSession::apply` only sends pause, speed and volume when they change. After every message, `app.rs` tells the game whether to run, how fast and how loud.
- **Slow work never runs on the UI thread or Iced's task pool**: scans, title screen captures, box art downloads and picture decoding go through `nubo_frontend::background::run`.
- **Box art is asked about once and fails quietly.** Once the library has a folder (in the browser, a game), a dialog asks whether to download box art (`Settings::box_art_asked` keeps the answer), and nothing is downloaded before the answer. A download that fails stops box art for the run without a toast; the settings' Library tab says why and offers Try again (`App::box_art_problem`).
- **The menus can't be remapped away.** They take fixed keys and buttons, never the player's bindings (`input::menu_action` for keys, `MenuButtons::action` for controller buttons; the one choice the player has is `Controls::menu_buttons`, which swaps the two face buttons that pick and go back: the right one picks by default, as on Nintendo's consoles, or the bottom one, as on Xbox), and a fixed menu button pressed in a menu does nothing else. To get into them while a game runs there is Esc and the controller's pause menu button, which can be moved but never cleared (`Controls::bind_button`). Waiting for a key or button in the settings gives up after five seconds (`CAPTURE_TIMEOUT`), since every controller button can be picked and none can cancel.
- **The library's cards have menus.** A right click, the "⋯" button or Select (on the keyboard the context menu key or Shift+F10) on a card opens its menu (`DialogKind::GameMenu`): Play, Console (the console and revision that game starts on, kept in `library.toml` and used before the settings' model, see `App::model_for`; its page lists the consoles, the one the game starts on in bold and the one it was made for saying so, with a button, or Right and Left on the D-pad, that unfolds and folds a console's revisions under it; picking one closes the menu, with a toast offering Undo, and a pick the settings would make anyway is kept as following them), Show in folder (in the browser, Remove from library), Remove from Continue playing and Delete save states. The sort button opens `DialogKind::SortMenu`; the order and the filter are this app's own settings (`settings.rs`). A game that starts, from a dropped file or Ctrl+O too, closes the settings, the wait for a key to bind and every library or settings dialog (`DialogKind::closes_when_game_starts`); only the box art and updates questions stay.
- **Where the player left off is saved as they play.** Besides when the game closes (`App::stop_game`), the Resume slot and the library card's picture are written after every minute a game runs and as soon as it stops running (the pause menu, a dialog, the settings, a window in the background), if it ran since the last save (`game::AutosaveTimer`, checked in `App::apply_to_game`). Quitting on macOS with ⌘Q, the app menu or the Dock ends Nubo without closing its window, and so does closing the browser's tab or a crash; this keeps all but the last minute. A pause menu page listing the slots is listed again after such a save, so "Where you left off" there is the moment the game paused.
- **A game continues only on the model it was left on.** Where the player left off (the automatic save) can load only on the model it was made on, so a game whose automatic save was made on another model than the one it is now set to start on (Automatic, the settings, its own menu or `--model`) asks first, in `DialogKind::OtherModel`, whether to switch: Switch to the new model starts from the title screen, and the automatic save is replaced once the new game has run a minute or stops running; Stay on the save's model continues from it and, once it has continued (not when the game doesn't start or the save doesn't load), keeps the game on that model from now on (in its own menu, unless the settings pick the save's model for it anyway, see `App::preference_starting_on`; not with `--model`). Meanwhile the game waits in `App::pending_start`, which also keeps the dialog the question took the place of (such as the box art question, open when a game is dropped on the window) and puts it back after the answer, Cancel included, or when another game starts instead.
- **Toasts stay out of the game's way.** Over a game only the newest toast shows, small and at the top (`Toasts::view`), and a message that comes again counts up instead of stacking. Loading a state, restarting, saving over a slot and resetting the settings keep what they replace (`playing::UndoPoint`, a state in memory, the slot's old file or the old settings) and say so in a toast with an Undo button.
- **Start over** (the About tab's row under the switch that looks for new versions, in one card with it) asks first in `DialogKind::ResetSettings`, a question with checkboxes: reset the settings (ticked at first), reset the controls (unticked at first, so players who set up their keys and buttons keep them), delete the in-game saves, delete the save states, remove the game folders, clear "Continue playing" (in the browser, "Remove every game" instead of the folders). Its button says what it does ("Reset", "Reset and delete", "Delete", "Clear") and is greyed out while nothing is ticked. Only what this build and run keep is offered (`App::reset_offers`): nothing but the settings and the controls with `--fresh`, and while a game is open, which would write its own saves again, the two deleting boxes are greyed out with a note to close the game first; a game that starts closes the question. The settings go back to `Settings::reset` (the window size, the controls and the folders stay, and the box art and update questions are asked again at the next start), and each game's picked model is forgotten. Saves are deleted in the background, and a game started meanwhile waits for them (`App::deletions_running`). Unless something was deleted, the toast that names what was done offers Undo, which puts the settings and the library's games back (`UndoPoint::Settings`) until a game starts.
- **The version names its build.** `version.rs` adds the commit and its date that `cargo xtask` passes in (`NUBO_COMMIT`, which `nubo_core::BUILD_COMMIT` keeps, and `NUBO_COMMIT_DATE`) to the version, as `0.10.0 (7c44d39 2026-10-16)`, for the About tab (with a "This build" button, linking to the commit on GitHub). `--version` prints it as the GNU coding standards ask: `nubo 0.10.0` alone on the first line, then `Built from commit 7c44d39 (2026-10-16)`, the copyright and the license (`command_line/parser.rs`); a plain `cargo build` shows only the version.
- **New versions are looked for only when asked.** On a start after the first game played, a dialog asks once (`Settings::check_for_updates`); with yes, each start looks up the newest release in the background (`nubo_frontend::updates`) and a newer one shows in the library's bar and on the About tab, whose buttons open the download page with this computer and version in its address (`updates::DOWNLOAD_PAGE`), so the page offers the right file and says how to update. Failures stay quiet.
- **Messages come in groups** (`GameMessage`, `LibraryMessage`, `SettingsMessage`, `WindowMessage`), each handled in its own file under `app/`. Screens are in `views/`, styles and themes in `ui/`.

## Where Things Are Kept

`nubo-frontend` keeps the data, through its `Storage` trait; with its `desktop` feature, which this app turns on outside the browser, that is files (`storage/files.rs`). Settings (`settings.toml`, with the controls and this app's own settings, `settings.rs`) are in the per-user config folder; everything else is in the per-user data folder, both picked by the `directories` crate: battery saves (`saves/`), the library cache (`library.toml`, `thumbnails/`, `title_screens/`, `box_art/`), save states (`states/<rom file name>/`) and cheats (`cheats/`). Screenshots go to `Pictures/Nubo` (or `screenshots/` in the data folder on a system without a Pictures folder).

## The Browser Build

- `nubo-frontend`'s session paced by the screen's refreshes (`session/screen_refresh.rs`) replaces the emulator thread: on each frame tick the app calls `run_due_frames`, which emulates the whole frames due by the refresh its own `requestAnimationFrame` clock saw, and `session/pacing.rs` decides how many and keeps the audio queue steady by nudging the sample rate. Controllers are read once per frame (`gamepads::next_event`).
- Settings, battery saves and cheats go to localStorage instead of files (`storage/local_storage.rs` in `nubo-frontend` names the keys), and save states, the library with its pictures and the games' files to IndexedDB (`storage/indexed_db.rs`), which `App::new` opens before it reads the library (`Message::StorageOpened`; until then the library page shows only its bar). The sound goes through cpal's WebAudio backend: the app turns on `nubo-frontend`'s `web` feature for wasm32. A write IndexedDB refuses, such as with a full disk, becomes a toast (`App::show_notices`). Updates and showing folders are desktop only; each module that differs has an `AVAILABLE` (or similar) flag.
- **The browser's library keeps the games themselves** (`nubo_frontend::library::KEEPS_GAMES`), since a page has no folders: "Add games" picks several files (`rom_picker::pick_many`, `LibraryMessage::AddGames`), every game picked with "Open game" joins the library, replacing one kept under the same file name (`App::keep_game`; games started from the library aren't kept again), a game's menu offers "Remove from library…" (`DialogKind::RemoveGame`, which deletes its file and pictures but keeps its saves), the settings' Library tab shows how many games it keeps and how much room they take instead of folders, and Start over's "Remove every game" deletes them all (so it counts as deleting, without Undo). Games start from their kept file (`nubo_frontend::rom::load`). Title screens are captured a few frames at a time, letting the page draw in between, and not while a game runs (`App::capture_title_screens`). The last game played that versions before kept in localStorage moves into the library once (`App::move_last_game`), and leaves localStorage only after its IndexedDB writes have committed (`nubo_frontend::storage::indexed_db::settled`); once the library keeps a file under its name (`Library::keeps_file_of`), or when it isn't a game, it is forgotten without being moved again. Screenshots are handed to the browser as downloads, and box art comes from the libretro collection's copy on GitHub, which lets pages read it.
- Code both builds share takes `Instant`, `SystemTime` and `Duration` from `nubo_frontend::time`, which re-exports the `web-time` crate (std's panic on wasm32; `iced::time` is the same types, for the UI code), and text that sets a font uses `theme::BODY_FONT` or `theme::HEADING_FONT` (the sans-serif font on the desktop, which on Linux `theme::use_desktop_font` makes the font the player picked for their desktop, as the desktop portal names it, and Fira Sans, which Iced bundles, in the browser): the browser has no system fonts, so `Font::DEFAULT` or another font of its own draws nothing there. Plain `text()` without `.font()` is fine, and so are the Lucide icons (`ui/icons.rs`), whose font the app loads itself.
- `deploy.yml` publishes the browser build to GitHub Pages on every push to main that passes CI.

## Packaging Files

`linux/` holds the menu entry and the AppStream metainfo, whose `<releases>` list holds the release notes. `windows/nubo.wxs` is the WiX script of the Windows installer (an MSI, with its own dialogs); its `UpgradeCode` must never change. `build.rs` gives `nubo.exe` its icon and file properties. They are built by the tasks in `xtask/` (see `xtask/AGENTS.md`).
